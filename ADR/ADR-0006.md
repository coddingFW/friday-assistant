# ADR-0006 — Interface como web app puro + resiliência de streaming

- **Status:** **Aceito**
- **Data:** 2026-08-01

## Contexto
ADR-0001 escolheu Tauri 2.0 + React. Na implementação (Fase 3), surgiram duas
decisões concretas: (a) como estruturar o frontend para servir desktop, web e
mobile sem duplicação; (b) como o backend deve se comportar quando o cliente
desconecta no meio de uma resposta em streaming (descoberto em teste real).

## Decisões
1. **Frontend é um web app puro.** O código React **não importa APIs do Tauri**;
   fala com o backend apenas via REST/WebSocket (`services/config.ts` centraliza as
   URLs; `VITE_BACKEND_HOST` permite o cliente mobile apontar ao Host na LAN). O
   shell Tauri (`src-tauri/`) apenas hospeda esse web app. Consequência: o mesmo
   bundle roda no navegador (dev/validação), no desktop Tauri e, futuramente, no
   mobile — sem reescrita e sem acoplar a UI ao runtime.
2. **Streaming resiliente à desconexão.** O handler WebSocket
   (`_handle_turn`) fecha o gerador de eventos (`aclose`) ao detectar desconexão,
   propagando o cancelamento até o stream do LLM. O `ConversationService.run`
   **não emite `yield` em `finally`** (isso quebra durante `GeneratorExit`); o
   estado `idle` é emitido nos caminhos normais/erro.

## Justificativa
- Desacoplar a UI do Tauri cumpre a topologia Host+Cliente e o objetivo de
  longevidade do ADR-0001 (um backend, vários clientes).
- A resiliência evita geração órfã (LLM continuando sem cliente) e o crash
  `RuntimeError: websocket.send after close`, observados em teste real.

## Impactos
- Estrutura `frontend/` (Vite + React + TS) + `src-tauri/` (Rust, buildável onde
  houver Rust). Rust não está instalado neste ambiente; a interface foi validada
  no navegador contra o backend + Ollama reais.
- Ajustes de robustez correlatos: `ollama_read_timeout` 120→300s (cold start em
  CPU) e `rag_timeout` 10→20s (agregação multi-motor da `ddgs`).
