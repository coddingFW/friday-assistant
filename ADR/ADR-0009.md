# ADR-0009 — STT: microfone no Host (1º StreamingSensor) + Whisper via Strategy

- **Status:** **Aceito**
- **Data:** 2026-08-10

## Contexto
A Fase 6 dá voz de entrada à Friday: falar em vez de digitar. Preciso decidir
onde o áudio é capturado, como é segmentado em falas, qual motor transcreve e
como a transcrição chega à conversa — sem quebrar a arquitetura (Host+Cliente,
camada de percepção, frontend desacoplado).

## Problema
O manifesto prevê a camada de percepção, mas nenhum sensor concreto existia. A
captura precisa virar `Percept(AUDIO)` sem o Brain conhecer o dispositivo; e a
transcrição é pesada em CPU (não pode travar o event loop).

## Alternativas
1. **Captura no navegador** (MediaRecorder) enviando áudio ao Host. Portável para
   clientes remotos, mas **não** é o "primeiro StreamingSensor concreto" pedido
   pelo manifesto (viraria `Percept` externo via `submit()`).
2. **Captura no Host** como `StreamingSensor` (`sounddevice`/PortAudio), emitindo
   `Percept(AUDIO)` pela camada de percepção. É o que o manifesto pede; o app é
   co-locado, então o mic do Host = mic do usuário.
3. VAD com `webrtcvad` (segmentação clássica) vs. **endpointing por energia (RMS)**.

## Decisão
Adotar **captura no Host como `MicrophoneSensor`** (alternativa 2):

- **`MicrophoneSensor`** (`perception/sensors/microphone.py`) — 1º `StreamingSensor`
  concreto. Captura 16 kHz mono int16 via `sounddevice` e segmenta em falas com um
  **endpointer por energia** (`EnergyEndpointer`, RMS em numpy): fala → silêncio
  prolongado encerra a utterance. Cada fala vira um `Percept(AUDIO)`.
- **`webrtcvad` foi descartado**: não tem wheel para o Python 3.14 desta máquina
  (tentaria compilar, exige Visual Studio). O endpointing por energia não tem
  dependência nativa a compilar e basta para push-to-talk.
- **STT = Whisper via faster-whisper/CTranslate2**, atrás de `STTProvider`
  (Strategy, igual a LLM/TTS). Inferência em **worker thread** (`asyncio.to_thread`)
  e **carga preguiçosa** do modelo (não pesa o startup nem os testes). 100% local
  após o 1º download do modelo.
- **Fluxo no `/ws/chat`** (reusa a memória de conversa): `listen_start` ativa o
  microfone via `SensorManager` e transcreve cada fala, emitindo `transcript`;
  `listen_stop` libera o dispositivo. Um **lock de envio** serializa as escritas
  no socket (transcrição vs. tokens).
- **O cliente decide o destino da transcrição** (auto-enviar vs. preencher o
  campo) — preferência do usuário, persistida no frontend. O backend só transcreve.

## Justificativa
- Concretiza a camada de percepção exatamente como o manifesto previu, sem tocar
  no Brain (que só consome `Percept`).
- Thread + carga preguiçosa seguem a lição do TTS (não bloquear o loop; startup leve).
- Energia como VAD remove uma dependência nativa problemática e é suficiente para v1.

## Impactos
- **Novos:** `backend/stt/` (ports, whisper, factory), `perception/sensors/microphone.py`,
  eventos `listen_start`/`listen_stop`/`transcript` e status `listening`.
- **Deps:** `faster-whisper`, `sounddevice`, `numpy` (webrtcvad **não**).
- **Frontend:** botão de microfone + toggle de auto-enviar (persistido) no `Composer`.
- **Escopo/limitações:** push-to-talk (a escuta contínua + wake word é a Fase 7);
  `perceive()` é consumido por uma conexão por vez (assunção de usuário único
  local); o 1º uso baixa o modelo do HuggingFace (depois roda offline).
