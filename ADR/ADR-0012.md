# ADR-0012 — Memória de longo prazo: persistência de conversas via SQLite (Repository Pattern)

- **Status:** **Aceito**
- **Data:** 2026-09-07

## Contexto
Até a Fase 8, a memória da Friday era só de **curto prazo**: o histórico da
conversa vivia em RAM, por conexão WebSocket (`history: list[ChatMessage]` em
`api/websocket/chat.py`). Ao recarregar a página ou cair a conexão, tudo se
perdia. O manifesto reserva para a Fase 9 uma **memória longa** com "SQLite via
Repository Pattern".

## Problema
- Persistir conversas entre sessões, offline, sem serviço externo nem chave.
- Não bloquear o event loop assíncrono do backend com I/O de disco.
- Manter o domínio desacoplado do mecanismo de persistência (poder trocar SQLite
  por outro backend no futuro sem tocar na regra de negócio).
- Suportar **múltiplas conversas** (retomar uma antiga, listar, apagar), sem
  inflar o escopo com busca semântica/embeddings ou cache — isso fica para
  incrementos futuros.

## Decisão
- **Camada nova `backend/memory/`** seguindo o mesmo Ports & Adapters de
  `rag/`, `stt/`, `tts/`:
  - `ports.py` — modelos `Conversation` / `StoredMessage` + a porta
    `ConversationRepository` (Protocol, assíncrona).
  - `providers/sqlite.py` — `SqliteConversationRepository`, o primeiro adapter.
  - `factory.py` — `create_conversation_repository(settings)` (Strategy).
  - `service.py` — `MemoryService`, a fachada de domínio que a API consome
    (mapeia `StoredMessage` ↔ `ChatMessage`, deriva título, grava o turno).
- **SQLite via `sqlite3` da stdlib** — zero dependência nova. As chamadas de I/O
  rodam em `asyncio.to_thread` (uma conexão única, serializada por lock),
  **não bloqueando o event loop** — mesma lógica que já isola o Piper (ADR-0007).
- **Múltiplas conversas.** O `/ws/chat` cria uma conversa nova na primeira
  mensagem (título derivado do texto) ou retoma a `conversation_id` enviada pelo
  cliente, semeando a janela de histórico a partir do banco. REST expõe
  `GET /api/conversations`, `GET /api/conversations/{id}` e
  `DELETE /api/conversations/{id}`.
- **Recall = janela das últimas N mensagens** (`history_max_messages`), lida do
  banco. Sem embeddings/vetor nesta fatia.
- **Degradação graciosa:** `FRIDAY_MEMORY_ENABLED=false` (ou falha do banco)
  volta ao comportamento anterior (só RAM), sem derrubar o turno.

## Justificativa
- Reusa o estilo arquitetural já consolidado (porta + fábrica + serviço).
- SQLite embarcado é 100% local, sem servidor, sem chave — cabe no manifesto.
- `to_thread` mantém o backend assíncrono responsivo mesmo em disco lento.
- Guardar só texto no histórico (imagens não são re-enviadas ao LLM em turnos
  seguintes) mantém o banco leve e o schema simples.

## Impactos
- **Backend:** novo pacote `memory/`; `settings` (`memory_enabled`, `db_path`);
  `utils/errors` (`StorageError`); `api/dependencies` (`get_memory_service`);
  `api/rest/conversations.py`; `api/websocket/protocol.py` (`conversation_id` na
  `UserMessage`; novo evento `conversation`); `api/websocket/chat.py`
  (resolução da conversa + persistência do turno); registro no lifespan.
- **Banco:** arquivo em `FRIDAY_DB_PATH` (default `./data/friday.db`,
  gitignored). Schema criado no startup com `CREATE TABLE IF NOT EXISTS` — sem
  framework de migração (KISS; volume baixo, um único usuário local).
- **Frontend:** nesta fatia continua igual (cada sessão inicia uma conversa
  nova, persistida em silêncio). A barra lateral de histórico (listar/retomar/
  apagar, consumindo o REST) é o **próximo incremento**.
- **Fora de escopo (futuro):** busca semântica/embeddings, cache de respostas,
  múltiplos modelos simultâneos, plugins, empacotamento.
